# Concurrency and locking (for agents)

Read this before changing checkout, reservations, payments, pharmacy reassignment, dispatch or background jobs. Design rationale:
DESIGN.md §10, sequence diagrams in docs/uml.md.

## Stock reservation (no overselling)

- Source of truth: PostgreSQL rows `stock_items(pharmacy_id, product_id, on_hand, reserved)`; `available = on_hand − reserved`;
  `CHECK (reserved <= on_hand)` is the last line of defence.
- `StockRepository` locks rows with `SELECT … FOR UPDATE … ORDER BY product_id`. **Always lock in product id order** — two baskets sharing
  products then never deadlock. The PK `(pharmacy_id, product_id)` matches that order.
- **Global lock order: the order row first, then stock rows.** Payment webhook, reservation expiry, pharmacy reject/timeout and cancel all
  lock the order row (`RowLocks.TryLockAsync`, `OrderRepository.GetForUpdateAsync`) before touching stock. Do not invert it.
- Waiting is bounded: `IUnitOfWork.ExecuteInTransactionAsync` runs `SET LOCAL lock_timeout = Database:LockTimeoutMs`; a timeout
  (`55P03`) becomes `409 stock.busy` (retriable).
- Transactions run inside the Npgsql execution strategy (`strategy.ExecuteAsync`): the whole operation is retried on transient errors
  (deadlock `40P01`, serialization `40001`, network), so **operations in a transaction must be idempotent** — no external calls inside.
- Checkout tries up to N ranked pharmacies; `stock.insufficient` in one rolls back and moves to the next.
- Tests: `CheckoutAndStockTests.ParallelCheckouts_NeverOversellScarceStock` (50 parallel checkouts, stock 10),
  `…_WithOverlappingBaskets_DoNotDeadlock`, `…_WhenStockRowIsLockedLongerThanLockTimeout_Returns409StockBusy`.

## Optimistic concurrency

`Order`, `Delivery` and other aggregates use PostgreSQL `xmin` as the concurrency token → `DbUpdateConcurrencyException` →
`409 concurrency.conflict`. Keys generated by the application (Guid v7) are `ValueGeneratedNever` — otherwise EF treats new child rows as
modified and throws a false concurrency error.

## Background jobs (multi-instance safe)

`PeriodicJob` runs each tick in a new DI scope. Work is claimed with `FOR UPDATE SKIP LOCKED LIMIT batch` (reservation expiry, pharmacy
acceptance timeout, dispatch retry), so several API instances can run the same job without a leader. A failing tick is
logged and retried on the next tick.

## Distributed locks (Redis)

`RedisDistributedLock` (`SET key token NX PX ttl`, release by Lua compare-and-delete). Used for courier assignment (`courier:{id}`) so two
dispatches never take the same courier. The database still guarantees it: partial unique index `ux_deliveries_active_courier`.

## Startup

Migrations, reset and seed run under `pg_advisory_lock` (`DatabaseMaintenance`, on a cloned connection) — with `--scale api=3` exactly one
instance migrates/seeds. TRUNCATE during reset uses `lock_timeout` + retry because consumers may hold locks.

## Messaging

MassTransit EF outbox: integration events are stored in the same transaction as the aggregate change and delivered with
`FOR UPDATE SKIP LOCKED`; the inbox deduplicates redeliveries. Consumers have `ConcurrentMessageLimit`; transient DB errors are retried,
`DomainException`/business errors go straight to `_error`.

## Tracking (in-process)

- GPS ingest → bounded `Channel<LocationHistoryPoint>` (`DropOldest`, backpressure) → `LocationHistoryWriter` batches with binary `COPY`.
- `TrackingPushThrottle`: per-order push throttling, a dictionary guarded by `System.Threading.Lock` (tiny critical section).
- `RoutingEtaService`: `SemaphoreSlim` limits concurrent ETA calculations.

## Do / don't

- Do keep transactions short; never call the PSP, Redis-heavy logic or HTTP inside a row-lock transaction.
- Do add new lock-taking code through `IUnitOfWork.ExecuteInTransactionAsync`.
- Don't lock stock rows without `ORDER BY product_id`; don't lock stock before the order row.
- Don't replace row locks with Redis locks for stock — Redis is not the source of truth and locks do not roll back with the transaction.
